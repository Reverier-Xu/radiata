# 审计记录：声明式异步架构与既有子系统（2026-10-09）

本目录仅保留审计记录与修复规划。每条发现记录：结论（CONFIRMED / PARTIAL / REFUTED）、
代码证据、机理、修复方向。核实方式：主会话直接取证（1-6）+ 四条只读复核 lane
（glm-5.3，7-16），全部结论以 `main`（`b3f742c`）为准。

## 图例

- **CONFIRMED**：机理与后果均被代码证据证实。
- **PARTIAL**：效果真实存在，但声称的机理有偏差，或仅部分场景成立；附带发现单独列出。
- **REFUTED**：声称的机理在当前代码中不存在；附带缺口（如有）单独列出。

## 1. 所有 effect 共享四个执行槽，本地写入被网络任务挤占 — CONFIRMED

- 证据：`src/runtime/task_manager.rs:41`（`TASK_RECONCILE_CONCURRENCY = 4`，单一信号量）、
  `:547`（构造）、`:932-936`（所有 kind 经同一 `semaphore.acquire()`）。
- 机理：join/connect 等网络类任务最坏可占槽至 dial 超时（10s 级），四个槽全部被占时，
  本地资源写入（put/delete/patch）排队等待——本地操作的可预期时延被网络健康度绑架。
- 修复方向：按 kind 分通道（本地类与网络类各自独立的并发额度，本地类保底 1-2 槽），
  或将执行槽划分纳入配置。

## 2. starvation 测试只覆盖单个挂起 join — CONFIRMED

- 证据：`tests/starvation.rs` 仅 `reads_and_packets_flow_while_a_join_is_wedged_on_a_silent_peer`
  一个测试，一个静默对端。
- 修复方向：补充四槽全部占满（四个挂起网络任务）时读/发包/本地写入仍流通的用例；
  与第 1 项的槽位划分修复同 commit 落地。

## 3. 路由策略与周期维护仍在循环内同步等待 — CONFIRMED

- 证据：`src/runtime/supervisor.rs:451`（`send_packet` inline await，含下一跳策略解析）、
  `:475-483`（recovery tick + trace/resource/receipt 三个 sweep inline）、`:486`
  （maintenance tick inline）。
- 机理：变更类操作移出循环后，循环内仍留有 IO/存储延迟来源；慢存储或慢策略解析时，
  读查询与包路由仍会被短暂阻塞。程度远低于重构前，但结构性问题未根除。
- 修复方向：tick 工作派生为任务（复用 task manager 的内部 kind）或独立 spawn；
  包路由臂保持 inline（它是背压点）但策略解析需确认无阻塞 IO。

## 4. packet 的 JoinSet 未回收，仅在 shutdown 清理 — CONFIRMED

- 证据：`src/runtime/` 全目录无 `join_next`；`supervisor.rs` 的 `tasks: JoinSet` 只在
  `finish_shutdown` 时 `tasks.shutdown().await`。
- 机理：出站包泵任务结束后其句柄在 JoinSet 中堆积至进程结束——长时间运行的节点
  元数据单调增长（单条很小，但违反仓库自己的 bounded task accounting 注释承诺）。
- 修复方向：select 循环加 `join_next` 回收臂（仅在非空时 poll），或在 recovery tick 中
  批量回收。

## 5. 观察 hook 持有执行槽并拖延 leave 关机 — CONFIRMED

- 证据：`src/runtime/task_manager.rs:937`——permit 跨整个 attempt body 持有；
  终态发布的 `observe()`（`:525-540`）在 body 内 await 全部 ActionHook；
  `leave_complete` 仅在 manager 处理 worker 报告后发送（`:734-746`）。
- 机理：一个永不返回的 ActionHook（或 ResourceHook.observed）使任务已显示 Succeeded
  却持续占槽，且 leave 的 ActiveLeave 关机被无限拖延。设计上"hook 不阻塞任务"的承诺
  只覆盖错误（warn-only），未覆盖挂起。
- 修复方向：终态相位先落表、槽位先释放，hook 观察移至槽外（ spawned 观察任务）；
  leave 信号改由任务表终态相位直接驱动（`f990376` 已部分修复，此处是残留面）。

## 6. caller expected 未进入最终提交边界，两个任务可形成竞态 — CONFIRMED

- 证据：`src/runtime/task_effects.rs:804+`（`reconcile_put_resource` 在**签名前**用
  `read_record_ctx` 检查 expected）；`src/resource/store.rs:80`（`commit_record_ctx`
  取新快照、以快照状态做 CAS，expected 不参与提交事务）。
- 机理：检查 expected →（异步签名，provider 可能是慢速 KMS）→ 新快照提交。两个并发
  CAS 任务都通过预检后，先提交者落地，后提交者的快照包含前者记录、其自身 CAS 通过、
  记录 wins_over 即覆盖——调用方的 expected 语义被静默违反。
- 修复方向：把 caller expected 传入提交边界（提交事务内以 expected 为 per-key 期望，
  或提交前在同一快照上复查 expected 与 winner 一致性），delete/patch 同查。

## 7. 恢复候选固定前缀/首 endpoint — CONFIRMED

- 证据：`src/runtime/recovery.rs:264`（仅 `endpoints().first()`）、`:319-338`（候选为
  BTreeSet 固定字典序前缀）；`src/membership/recovery.rs:158-166`（`take(fan_out)`，
  熵只用于退避 jitter）；`src/membership/degree.rs:112-120`（唯一带随机化的 degree
  平面在零会话时 `dial_budget = 0`——恰好是 recovery 唯一活跃的状態）。
- 机理：完全隔离的节点每轮拨同样的前缀成员、每个成员只拨其首个 endpoint；前缀全挂
  或多宿主成员仅首 endpoint 不可达时，恢复永远不重试其余候选。
- 修复方向：`next_step` 轮换候选窗口（轮转游标或熵洗牌）；`known_online_members`
  携带全部 endpoint 并支持端点级 failover。

## 8. 临时 SPKI pin 阻碍服务器换证回连 — CONFIRMED

- 证据：`src/runtime/task_effects.rs:307-311`（唯一记录点：join 时）；
  `src/runtime/supervisor.rs:840-845`（所有成员拨号强制 pin）；
  `src/transport/verify.rs:88-94`（SPKI 不等即 TLS 失败，应用层身份证明没机会执行）；
  `src/session/driver.rs:109-113`（进程内存表，无 rollover/淘汰）。
- 机理：对端合法换证（同身份密钥、新叶证书）后，本进程所有出站拨号在 TLS 层永久
  失败；recovery 按退避曲线无限重试同一 pin。仅进程重启（丢 pin，且不再重新 pin）
  或重新 join 可恢复。
- 修复方向：pin 失败时回退一次 Merge 信任拨号，应用层身份认证通过后再重录 SPKI
  （身份权威本就在证明层）；或按 peer 保留最近 N 个锚。

## 9. 旧 watermark ack 丢失导致 busy — REFUTED

- 证据：cleanup checkpoint 是无确认协议的 max-wins 单行记录
  （`src/identity/cleanup.rs:243-259, 341-377`，旧水位静默 no-op 成功）；签发侧本地
  提交即完成，不等任何对端确认（`src/runtime/task_effects.rs:595-605`）；传输 ack 按
  TraceId 配对且有 5s 有界等待（`src/sync_common.rs:183-296`）；对账 DONE 收据与
  token 无关（`src/reconcile/engine.rs:530-535`）；卡住的对账轮由节奏 ROOT 强制解锁
  （`engine.rs:632-660`）。
- 结论：所描述的机制不存在（疑似描述了已移除的 WatermarkWalk 旧设计）。无需修复；
  可在 `identity/cleanup.rs` 加一行"checkpoint 按设计无 ack 协议"注释以防重复审计。

## 10. endpoint 更新丢节点 labels — PARTIAL（效果真实，机理归因错误）

- 声称的 patch 路径是干净的：`apply_metadata_patch` 保留 labels（`src/membership.rs:203,231`），
  `reconcile_patch_metadata` 与对端同步安装同样保留。
- **真实丢失路径**：`src/membership/sync.rs:694-703` `ensure_local_descriptor` 在
  endpoint 集合漂移时用 `NodeDescriptorV1::new(...)` 重建描述符——**不带 `.with_labels()`**，
  labels 默认为空（`src/membership.rs:70-83`）。触发面：任何 listener 增删后的维护 tick，
  或任何与 `published_endpoints` 不一致的 endpoint patch。高 revision 记录把清空传播到
  所有对端。
- 附带：无测试覆盖描述符 labels 在维护重写下的存活（资源 labels 有，节点 labels 没有）。
- 修复方向：`ensure_local_descriptor` 重写时携带既有 labels；补回归测试（patch labels →
  增删 listener → 一个 tick 后本地与对端 labels 均存活）。同时明确"patch 了但未监听的
  endpoint 是否应存活"——目前同一重写会静默回滚它。

## 11. 传输中断伪装成正常 End — PARTIAL（中继投递确认；直连场景类型正确）

- 证据：`src/session/stream.rs:492` → `src/routing/forward.rs:275-305`
  `close_for_peer` **合成** wire 合法的 `EndFrame{trace_id}` 发往下游；
  `src/packet/wire.rs:117-118` End 帧无原因码；目的端 `src/session/inbound.rs:186-189`
  以正常 `StreamItem::End` 交付——消费者对"截断"与"完整"不可区分。
- 反证（直连安全）：`src/packet/mod.rs:575-592` `channel_body` 在无 End 收尾时补
  `Err(StreamInterrupted)`，有测试钉住。
- 附带：发送端与接收端对同一投递结论相反（route record 可能被翻成 Failed，而消费者
  看到了"正常结束"）。
- 修复方向：End 帧加类型化终态判别（如 reason 字段或独立 Rst 帧），中继透传，目的端
  映射为 `Err(StreamInterrupted)`；补"中继腿中段死亡"回归测试。

## 12. reader 取消连带取消 consumer — REFUTED（附带一个 P2 缺口）

- 证据：消费者 drop 只做本地清理（`src/session/inbound.rs:427-435`）；会话任务仅在
  节点 shutdown 时中止；read_loop 被取消时其 consumer JoinSet 是**丢弃（detach）**而非
  abort。
- 附带缺口（P2）：read_loop 被取消的路径不生成 drain 任务（`inbound.rs:250` 仅在正常
  退出时执行），consumer 任务变为无归属——shutdown 不等、recovery 收割器不可见。
- 修复方向：read_loop 入口处建 drop-guard，保证取消路径同样注册 drain。

## 13. 迟到的 ack / 旧会话清理缺少归属校验 — PARTIAL

- **确认的子机理**：ack 仅按 trace_id 归属（`src/session/inbound.rs:205-234`），不校验
  接收会话是否仍是该 hop 的当前下游。hop 超时切换到 C2 后，来自 C1 的迟到 ack 可：
  (a) 触发第二次 `on_downstream_failure`，吞掉 C2 的 live pending entry；
  (b) 错误清除 live hop 的重试臂；(c) 把 route record 误翻为 Failed。
  （`src/routing/forward.rs:419-551`）
- 驳回的子声称：跨会话世代的 pending_acks 互串不存在（pending map 按 run_session 实例
  隔离，退休时排空）。
- 附带（P2）：`maybe_prune_recovery_edges` 扫描与 `retire_session` 之间非原子
  （`src/runtime/recovery.rs:144-176`），窗口内被替换的条目可能被误收割（flag 归属
  而非世代归属）。
- 修复方向：Ack 分支校验接收会话 == hop 当前 downstream（指针等同或尝试 nonce）；
  prune 改为锁内按条目身份退休并复核 `recovery_dialed`。

## 14. redb 取消后晚提交 — PARTIAL（机制确认；后果在设计内闭环；一处潜伏 P2）

- 机制确认：`src/storage/redb/store.rs:160-167` commit 经 `spawn_blocking`，调用方
  future 被 drop 后阻塞任务 detach 并继续 `write.commit()`——取消后写入仍落盘。
- 后果驳回：引擎的冻结/对账闭环（`src/storage/mod.rs:184-201, 578-616`）保证不产生
  "未提交"的错误裁决——取消的提交无裁决、槽位冻结、重启 reconcile 按 durable 收据分类；
  journal 与写入同事务（`src/storage/pending.rs:488-542`）。
- 潜伏 P2：`ProviderCall::drop` 在 detach 任务完成前清 `provider_call_active`，窗口内
  的 `begin_reconcile` 可能读到无收据并误判 Aborted。当前不可达（生产 reconcile 只在
  重启或已完成调用后发生）。
- 修复方向：由阻塞任务自身在完成时落定槽位（或 begin_reconcile 等待在途句柄），
  不以 future-drop 推断 settled。

## 15. caller feature registry 没有进入握手 — CONFIRMED（P1 功能缺陷）

- 证据：offer 构建正确合并（`src/runtime/supervisor.rs:227-231`）；但
  `src/session/driver.rs:328`（响应方 accept）、`:437`（发起方 merge）、`:514`
  （发起方 member）三处握手全部以 `FeatureRegistry::builtin()` 构建——caller 注册表
  只在线上 offer 里出现，选择阶段被丢弃（`src/protocol/selection.rs:106-124` step 3
  丢弃未知 tag）；caller 把自定义 feature 标为 required 则握手 100% 失败
  （`UnknownRequired`，`selection.rs:139-150`）。
- 后果：违反 `ExtensionRegistry::register_feature` 文档承诺（"offered and intersected
  at handshake time"）；caller feature 拥有的协议在任何会话上永不可准入。
- 修复方向：合并后的 registry 随 offer 一起注入 SessionDriver（Arc 共享），三处握手
  统一使用；补双节点测试断言注册 feature 存活于选择结果。

## 16. 取消事件 recv 破坏订阅 — PARTIAL

- 确认的一半：`EventSubscription::recv()` 取消不安全——`event.rs:66` 先把状态置为
  Terminated，receiver 活在被 drop 的 future 帧里；之后所有 recv/poll_next 静默返回
  Closed/None，与正常关闭不可区分（`src/node/event.rs:65-83`）。
- 驳回的一半：`poll_next` 路径是取消安全的（InFlight 存入 self.state，:152-160）；
  无 panic、无死锁、无丢失唤醒。
- 修复方向：`recv()` 改为与 `poll_next` 相同的取出-存回模式（取消后 receiver 保留在
  self.state）；补取消安全性测试（timeout 包裹 recv 后订阅仍可用）。
