# A08: Lazy descriptor publication uses a detached spawn outside the shutdown drain

- Verdict: CONFIRMED (core claim fully verified; two of the three claimed consequences hold in a refined form — see Root cause/Impact)

- Evidence:
  - The detached spawn, unregistered — `src/runtime/task_effects.rs:891-921`:
    ```rust
    pub(super) fn kick_self_descriptor_publication(deps: &Arc<OperationDeps>) { ...
      let deps = Arc::clone(deps);            // :906
      tokio::spawn(async move {               // :907 — handle discarded, never stored
        ...
        if let Err(error) = ensure_self_descriptor(&deps).await { ... }  // :914
      });                                     // :921
    ```
    The task holds `Arc<OperationDeps>` → `EffectPlanes.context: Arc<LocalIdentityContext>` (`task_effects.rs:56`) → `MetadataStore` (`src/identity/lifecycle.rs:59-60,70-72`), i.e. the node's exclusive storage handle.
  - The shutdown drain never touches it — `src/runtime/supervisor.rs:559-611` (`finish_shutdown`): the task manager drains (`:576 manager.drain().await`), the supervisor's `JoinSet` shuts down (`:583 tasks.shutdown().await`), and only handles collected by `into_dependencies` (`:913`) are awaited inside the 3s `CONNECTION_TASK_SHUTDOWN_GRACE` window (`:591-605`). `into_dependencies` collects exactly: sync driver (`:923 driver.abort()`), tick workers (`:931`), accept loops (aborted, `:937-945`), and `connection_tasks` (`:951-952 drained.extend(handles.drain(..))`). The lazy-publication handle is in none of these registries.
  - The codebase's own enrollment pattern exists and is used by every comparable spawned task: `task_effects.rs:384-389` (`spawn_tracked`: spawn then `tasks.lock().push(handle)`), recovery dials (`src/runtime/recovery.rs:439-441`), degree-maintenance dials (`src/runtime/degree.rs:353-355`), accept loops (`task_effects.rs:1468-1476`). Only the lazy publication skips it.
  - The in-code justification is factually wrong — `task_effects.rs:881-883`: "The task is deliberately detached — … the same bounded-detached shape as the maintenance plane's in-flight dials." The maintenance dials are *not* detached: they are registered in `connection_tasks` (`degree.rs:353-355`, `recovery.rs:439-441`) and drained at shutdown.
  - The violated design contracts — `task_effects.rs:12-16`: "a caller holding a handle never keeps the metadata store's **exclusive lock alive past node shutdown**"; `supervisor.rs:584-586`: "Drain the returned task teardown so **every storage capture is dropped before the shutdown reply returns** (a restarted node on the same factory must not race the release)."
  - Why the lock matters — `src/lib.rs:150-154` (`redb_store`): "holds one exclusive lifetime lock per open store; a second concurrent open fails typed instead of aliasing the store"; contract test `src/storage/contract/engine.rs:1396-1413`: second open → `ErrorKind::StorageLocked`, freed only by dropping the first handle.
  - Trigger path — read views call `kick_self_descriptor()` (`src/runtime/views.rs:47`), invoked from `member()`/`page_members()` on the supervisor loop, so a kick can be mid-commit when `Control::Shutdown` arrives.
  - No cancellation hook: the spawned body never polls `planes.shutdown` (the watch every kept session observes, `task_effects.rs:79`).

- Root cause: `kick_self_descriptor_publication` off-loads the descriptor ensure to a raw `tokio::spawn` whose `JoinHandle` is discarded, unlike every other spawned runtime task which registers in `ConnectionTasks`. Concrete interleaving: (1) a member read on a listenerless node passes the stamp/slot gates and spawns the ensure; (2) the ensure is mid `store_descriptor_ctx` commit (fsync on redb — the slow case the lazy path exists for); (3) `shutdown()` arrives; (4) `finish_shutdown` drains manager/JoinSet/connection_tasks, none of which include the lazy task, and returns the `ShutdownOutcome` while the task still runs and still owns `Arc<OperationDeps>` → the exclusive storage handle.

- Impact: every embedder that reads members on a listenerless node and then shuts down. Not use-after-free — the Arcs keep the store alive — but the inverse, which the codebase documents as a contract breach: (a) the storage exclusive lifetime lock outlives the shutdown reply, so an immediate restart on the same factory fails with `StorageLocked` until the stray commit finishes (tests already fight this class of race: `tests/secure_join.rs:497`, `tests/resource_operations.rs:406`); (b) if the embedder tears down the tokio runtime right after the reply, the task is killed mid-commit — publication lost or left as an indeterminate commit needing journal reconcile on reopen (self-healing: the next incarnation's stamp starts `None`, so the first member read re-kicks; `task_effects.rs:155`); (c) the paired `MemberChanged` event/revision bump can fire after `lifecycle.stop` (benign: `EventHub::emit` is non-blocking, `src/node/event.rs:235-239`). Severity P1: bounded to one in-flight task (single-flight gate) doing one commit, so the window is one storage-commit latency, but on the slow-storage deployments this path targets that is exactly seconds, and the failure mode is a hard typed startup error. Permanent until fixed.

- Suggested fix direction: enroll the handle in the existing `ConnectionTasks` registry — capture the `tokio::spawn` result and push it via the same `planes.connection_tasks.lock().push(handle)` shape the dials use (or reuse the `spawn_tracked` helper at `task_effects.rs:384-389`). This makes shutdown await the one commit inside the existing 3s cooperative window and abort+reap the straggler, releasing the store Arc before the reply — the exact precedent of audit finding #19 for recovery dials (`recovery.rs:970-977`). The abort path is already safe: `PublicationSlot::drop` releases the single-flight flag on cancellation, and an aborted commit degrades to the store's existing indeterminate-commit reconciliation. Also correct the stale comment at `task_effects.rs:881-883`. No unsafe, no unwrap; tracing already covers the failure path.

- Validation ideas:
  1. Mirroring `shutdown_aborts_and_awaits_an_in_flight_recovery_dial` (`recovery.rs:977`): with a fault-injecting provider whose descriptor commit parks, kick via a member read, then `client.shutdown()`; assert the handle appears in `connection_tasks`, the reply resolves inside `CONNECTION_TASK_SHUTDOWN_GRACE`, and the park is released (task aborted and reaped).
  2. The sharpest assertion: after the shutdown reply returns, `factory.open(StoreRequirements::metadata())` on the same factory must succeed immediately (no `StorageLocked`) — proves the storage capture dropped before the reply.
  3. Happy path: a slow-but-completing commit finishes before the reply, the descriptor is durable, and the `MemberChanged` pair fired before `lifecycle.stop`.
  4. Slot hygiene: after an aborted publication, a restarted incarnation on the same factory re-kicks and publishes (stamp starts unset).
